The bottom line

For Legal EASE as it runs today — a single node, ~9k–100k vectors, embedded/serverless, latency-sensitive — ChromaDB is the pragmatic choice: sub-2 ms queries, 6× faster index builds, lower memory, and trivial in-process persistence with no server to operate.

For an institutional / production platform — millions of vectors, concurrent writers, high availability, best-in-class recall and quantization — Qdrant in server mode is built for it. We measured that server too (§7): it indexes faster than Chroma and deletes ~4× quicker, and cuts query latency 2–3× — though in-process Chroma keeps a single-query latency edge because Qdrant pays a per-request network hop. Chroma's recall gap is tunable via HNSW. Crucially, across the actual legal questions we tested, the two produced 98%-identical grounded answers — so the choice is about latency, scale, and operations, not answer quality.

01 — Methodology

How we measured it

The benchmark is designed so that only the vector database varies. Everything upstream — corpus, embedding model, query set — is held constant, and each engine is measured in isolation, five times.

Controls

  • Identical vectors. The 9,063 InLegalBERT embeddings are computed once and fed to both databases — no re-embedding, so embedding cost never confounds the result.
  • Isolated subprocess. Each engine runs in its own process; the parent polls RSS to capture a clean peak-memory figure per database.
  • Exact ground truth. Recall is measured against a brute-force NumPy cosine scan of all 9,063 vectors — the true top-k, not an approximation.
  • Five runs. Every metric is repeated 5× and reported as mean ± std, so variance is visible and the numbers are reproducible, not single-shot.

Environment & caveats

  • Hardware. Windows workstation, CPU-only, local SSD. No GPU; both engines are on equal footing.
  • Qdrant ran in local/embedded mode (the Python file-backed client), which is a development convenience, not its performance configuration — the Rust server is materially faster (see §6).
  • Chroma's persistent client (hnswlib + SQLite) is its normal single-node mode, so its numbers reflect a realistic deployment.
  • Queries: 28 realistic Indian-contract-law questions; latency is 25 timed repetitions per query per run, top-k = 10.

Reproduce: python scripts/index_knowledge_base.py --store both → python scripts/benchmark_vector_dbs.py --runs 5 → python scripts/compare_answers.py.

02 — Background

Meet the two databases

Both are open-source (Apache-2.0) vector stores, but they come from different design philosophies — which is exactly why their benchmark profiles diverge.

ChromaDB
Python-first · embeddings database for LLM apps

An AI-native vector store built for developer velocity. Its persistent client runs fully in-process (HNSW via hnswlib, metadata in SQLite), so there is no server to stand up — you pip install and go. A client/server mode and Chroma Cloud exist for scaling out.

  • Trivial embedded persistence; minimal ops
  • Very low query latency & memory in-process
  • Fast index builds
  • Default HNSW favours speed over recall (tunable)
  • Single-node focus; clustering/HA less mature
Qdrant
Rust engine · purpose-built vector search

A dedicated vector search engine written in Rust, built for production scale. Its server offers gRPC/REST, typed payload filters with payload indexes, vector quantization (scalar/product/binary), memory-mapped & on-disk vectors, and sharding / replication / HA. A local embedded Python mode exists for development (what we benchmarked here).

  • Excellent recall out of the box
  • Horizontal scale, HA, quantization, rich filtering
  • Smaller on-disk footprint
  • Heavier to operate (run a server)
  • Local/embedded mode is dev-only & slower

05 — Retrieval quality

Recall — do we get the right results?

Recall@10 measures how many of the true top-10 nearest vectors (by exact cosine) each engine's approximate search actually returns. This is where they genuinely diverge: Qdrant is perfect; Chroma's default HNSW misses ~24%.

recall@10 vs exact brute-force 1.0 = returns the true top-10 every time · mean ± std
Chroma
0.761 ±0.017
Qdrant
1.000 ±0.000

Why the gap — and why it's tunable

Chroma's default HNSW search breadth (ef) is tuned for speed, so it explores fewer candidates and misses some true neighbours. Qdrant's defaults favour accuracy. This is a configuration difference, not a capability ceiling — raising Chroma's ef_search / construction parameters trades some of its large speed surplus for recall. The 0.761 is the out-of-the-box number an unaware team would ship.

Stability across the 5 runs

Qdrant returns exactly the true top-10 on every run (recall = 1.000, std = 0). Chroma's recall wobbles between runs (0.732–0.782) because HNSW graph construction is randomised — visible below.

Why so high despite a 0.76 overlap? Because the decisive, high-signal chunks (the relevant statute, the "liquidated damages" definition, the matching red-flags) are retrieved by both stores. The recall gap lives in the low-ranked tail that the LLM barely uses. Example — “Is the non-refundable security deposit enforceable in India?”

ChromaDB · confidence: high
“No … the clause stating the security deposit is ‘NON-REFUNDABLE … forfeited to the Lessor in all circumstances’ is unlikely to be fully enforceable. In India, courts treat such clauses, if essentially a penalty, under the principles of liquidated damages … will only award reasonable compensation … This is grounded in Section 74 of the Indian Contract Act, 1872.”
Qdrant · confidence: high
“While the Rental Deed states … the deposit is ‘NON-REFUNDABLE and shall stand forfeited … including normal expiry,’ its enforceability is subject to scrutiny. As per the definition of Liquidated damages (referencing Section 74, Indian Contract Act, 1872), courts award only reasonable compensation … and will not enforce the sum if it is determined to be a penalty.”
Both answers grounded on the same retrieved set: Indian Contract Act §58 & §36, the “Liquidated damages” glossary entry (§74), red-flag references, and two Supreme Court judgments — identical sources, identical retrieval scores. Similarity: 0.979.
07 — Local vs Server

We ran the Qdrant server — and the story flips

Everything above measured Qdrant in local / embedded mode (a pure-Python, file-backed client). That is not Qdrant's performance path. So we stood up the real Rust server (Docker, v1.18.3) and re-ran all five iterations against it over gRPC. The result reverses two headline verdicts.

What server mode changed

Qdrant server indexes 9× faster than its local mode — and now beats Chroma (6.2 s vs 9.3 s). It deletes 8× faster than local and ~4× faster than Chroma (37 ms vs 164 ms). Query latency dropped 2–3× (filtered latency fell from 93 ms to 27 ms). Recall stayed perfect (1.000). The one thing server mode does not win is single-query latency — and that gap is transport, not search (see below).

Why Chroma still wins single-query latency — and why that's expected

ChromaDB runs in the same process as the application: a query is a function call with zero network cost. Qdrant, even on localhost, is a separate server — every query pays a gRPC round-trip and (de)serialization. That per-request transport (~10–15 ms here) is the residual gap, not slower vector search. It's the classic embedded vs client-server trade-off: in-process wins a single synchronous query; a server wins on concurrency, horizontal scale, isolation, and shared access by many clients — which is exactly what production platforms need. Under concurrent load or batched queries, the server's throughput advantage reasserts itself.

Measured on the same machine: Qdrant server disk 85 MB (matching local), container memory ~450 MB peak during bulk load and 85 MB idle. The harness reports a smaller RSS for the Qdrant runs because the vector engine now lives in the container, not the Python client.

11 — Decision

Which should you choose?

Choose ChromaDB when…
  • You're single-node, ≤ ~100k–1M vectors
  • Latency is critical and you want zero server ops
  • You're prototyping or shipping an MVP fast
  • Memory is tighter than disk
  • …and you'll tune HNSW ef if recall matters
Choose Qdrant when…
  • You need millions of vectors, HA, horizontal scale
  • Out-of-the-box recall accuracy is non-negotiable
  • You want quantization & disk-efficient storage
  • Rich, indexed metadata filtering at scale
  • …and you'll run the server, not local mode

Recommendation for Legal EASE

Stay on ChromaDB for the current product — it's faster, lighter, and the answer quality is indistinguishable from Qdrant's on real legal questions (0.98 similarity). Keep the pluggable VectorStore abstraction and the Qdrant backend in place: when the corpus grows past a single node or recall SLAs tighten, flip VECTOR_DB=qdrant against a Qdrant server — no application rewrite required. Before that switch, close Chroma's recall gap by raising its HNSW search breadth and re-running this benchmark.
